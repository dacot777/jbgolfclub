# 성과 대시보드에 캡처 확인 자료 반영

**최신 기준 구간 요청:** 사용자가 현재 수치를 2026-10-29~2026-11-06 첫 보고 기록으로 지정했습니다. 원본은 유지하고 사용자 지정 기준의 누적/기간 기록을 추가합니다. 이후 누적 차이로 기간 증가분을 보관하고 전체 누적은 최신 lifetime만 선택합니다. 주간업무보고 메뉴는 제거하며 향후 분석 코멘트를 저장해 표시합니다. [증가분 운영 기준](PERIOD_LEDGER.md).

**최신 제출 화면 요청:** ‘핵심 성과’ 제목·카드·합계 안내를 `SHOW_KPIS=false`로 잠시 숨깁니다. 조회 기간과 이력에는 실제 수치가 있는 저장 기록의 정확한 기간만 표시합니다. 날짜 슬롯·빈 주차·월·가짜 레코드를 미리 만들지 않습니다. 현재 두 광고는 모두 집계 날짜가 미확인인 누적 기록이라 ‘전체 누적 성과’만 선택할 수 있으며 빈 주간 표는 표시하지 않습니다. 데이터는 삭제하지 않습니다.

사용자 최종 의도(2026-11-06)는 **채팅으로 게시물 링크와 인사이트 캡처를 전달하면, assistant가 정확히 읽고 분석해 기존 성과 대시보드의 숫자를 갱신하는 것**입니다. Facebook/Meta 자동 연동을 준비할 때까지 이 절차로 진행합니다. 별도 인사이트 기록 메뉴·이미지 업로드·사용자 수치 입력·브라우저 백업 UI는 제공하지 않습니다.

## 현재 사용 방식

- 기존 Workers 사이트의 성과 대시보드가 `GET /api/performance`로 검토된 자료를 읽습니다. 실제 자료가 있으면 합성 예시 화면 대신 실제 캡처 기준의 핵심 지표·광고 상세·게시물 링크·기간 선택을 표시합니다.
- 사용자는 채팅으로 자료를 전달합니다. assistant가 수치를 대조해 기존 D1에 반영한 후 사용자는 사이트를 새로고침합니다. 이번 구현이 매주 자동으로 캡처를 확보하거나 Meta 데이터를 수집한다는 뜻은 아닙니다.
- 사용자 후속 디자인 요청으로 ‘캡처 당시 활성’, ‘캡처 확인 자료’, 캡처 안내 배너와 보고 복사 버튼을 화면에서 제거했습니다. 보고 제목은 **한 줄 결과**이며 광고별 핵심 결과와 비용만 간결하게 표시합니다. 원본 출처·상태는 서버 자료에 유지합니다. 방패 로고와 실제 게시물 썸네일은 [브랜드 자산 기록](BRAND_ASSETS.md)을 따릅니다.
- 조회 기간에는 실제 지표가 있고 집계 시작일·종료일이 확인된 기록만 중복 없이 표시합니다. 예를 들어 11월 1~7일 자료가 실제 저장된 뒤에만 그 날짜가 선택 항목에 추가됩니다. 월 경계를 넘는 자료도 원래의 정확한 날짜 그대로 조회합니다. 원본 기간을 임의로 나누거나 배분하지 않습니다.
- 누적 자료와 날짜가 확인된 자료를 구분합니다. 저장 기록이 없는 기간은 선택 항목이나 이력 표에 만들지 않습니다. 실제 기간 중 일부 광고의 수치가 없으면 대기 상태와 대시로 구분하고 0으로 채우지 않습니다.

## 데이터와 보관

마이그레이션 `0002_reviewed_performance.sql`은 기존 무료 D1에 `reviewed_ads`, `reviewed_snapshots` 두 테이블과 인덱스만 추가합니다. 인증 테이블·기존 데이터·암호화 Secret은 유지합니다. 추가 유료 서비스, AI/OCR API, 계정 가입, 전역 도구 설치는 없습니다.

- 공유 계약: `src/lib/reviewed-performance-types.ts`.
- 광고에는 표시 제목·정규 Instagram 게시물 URL·목표·캡처 당시 상태·광고 설정 일정을 저장합니다. URL의 추적 매개변수는 제거합니다. 게시물 shortcode와 광고/광고 계정 ID를 혼동하지 않습니다.
- 스냅샷마다 별도 ID·광고 ID·성과 기간 또는 null·누적/선택 기간 구분·화면에 나온 집행 일수·수치·자료 확인 시각·출처 설명을 보존합니다. 자료 확인 시각을 성과 종료 시각으로 취급하지 않습니다.
- 새 기간은 새 스냅샷으로 추가합니다. 과거 자료를 삭제하거나 최신 주의 값으로 덮어쓰지 않습니다. 같은 광고/기간의 정정도 새 검토본으로 추가하면 최신 확인 시각의 1건만 화면 집계에 사용됩니다.
- 실제 회사 자료는 `.worker-build/` 등 Git 제외 경로에서 준비해 파라미터 바인딩한 D1 쿼리로 반영합니다. 공개 저장소·번들·테스트에는 넣지 않습니다. 반영 전 기존 검토 자료를 비공개로 보관하고, 반영 후 수치를 읽어 대조합니다.
- `GET /api/performance`는 현재 공개 성과 대시보드용 읽기 전용 응답입니다. 공개 쓰기 API는 없습니다. 계정 ID·원본의 추가 관리 메타데이터·인증 값은 반환 필드 목록에서 제외합니다. 응답은 no-store, 기존 서버의 보안 헤더를 유지합니다.
- 최대 광고 2개·스냅샷 2,000건 범위이며 범위 초과·잘못된 자료·DB 장애는 503으로 처리합니다. 오류를 실적 0이나 인증 성공으로 바꾸지 않습니다.
- 기존 GitHub Pages에는 서버 조회를 활성화하지 않습니다. 실제 자료의 조회 주소는 Workers 사이트입니다.

## 숫자와 기간의 정확성

광고 일정과 성과 집계 기간은 다릅니다. ‘전체 기간’, ‘7일 동안 집행’과 광고 시작/종료 예정일만 있는 캡처는 정확한 성과 시작일·종료일로 확정할 수 없습니다. 전달된 두 광고 모두 실제 수치를 보여주되 **전체 기간 누적·집계 날짜 확인 중**으로 저장하고 특정 주에 넣지 않습니다. 두 번째 광고는 링크 클릭 수·클릭당 비용·랜딩 페이지 조회를 별개 지표로 보존하고 총예산을 일일 예산으로 표시하지 않습니다. 타겟 상세의 지역·연령·관심사·설정 토글은 명시된 값만 기록하고, 막대그래프의 수치는 추정하지 않습니다.

- 조회수, 조회한 사람, 프로필 방문, 웹사이트 방문, 링크 클릭, 게시물 참여, 공감, 3초 이상 재생은 원문 지표 그대로 유지합니다. 조회수를 노출로, 조회한 사람을 도달로 바꾸거나 조회수를 분모로 CTR을 계산하지 않습니다.
- 비용은 캡처의 표시값을 보존하고 해당 목표 결과 수와 지출로 교차 확인합니다. 서로 다른 목표의 결과·결과당 비용을 합치거나 단순 평균하지 않습니다.
- 주간 집계는 `selected_period`이면서 시작일·종료일이 정확히 같은 자료만 선택합니다. 누적 자료는 주간 집계로 재분류하지 않습니다. 같은 광고/기간의 여러 캡처는 최신 검토본 1건만 사용합니다.
- 여러 광고의 합계는 정확히 같은 선택 기간일 때만 계산합니다. 같은 지표의 값이 모두 있어야 합산하며 누락과 0을 구분합니다. 여러 광고의 고유 인원과 결과당 비용은 합산하지 않습니다.
- 이전 기간 비교는 동일 길이의 바로 이전 기간, 동일한 광고 집합, 양쪽에서 확인된 같은 지표에만 적용합니다. 불충분하면 ‘비교 자료 없음’을 표시합니다. 원래 없는 일별 수치를 만들어 그래프를 그리지 않습니다.

## 후속 자료 반영 절차

1. 게시물 URL·표시 제목과 캡처 원문 수치를 검토합니다. 성과 기간이 보이지 않으면 기간은 null로 남깁니다. 광고 설정 일정은 별도 필드에 기록합니다.
2. 비공개 payload를 서버 검증 함수로 검증합니다. 원본의 숫자·목표별 비용을 교차 확인하고 실제 광고 ID/게시물 식별자를 구분합니다.
3. 기존 `reviewed_*` 테이블의 자료를 비공개로 보관한 뒤 광고 메타데이터를 갱신하고 새 스냅샷을 추가합니다. 인증용 테이블은 수정하지 않습니다.
4. API와 실제 대시보드에서 해당 광고·집계 기간·숫자를 대조하고 과거 주간 기록이 유지되는지 확인합니다. 새로운 주가 추가됐다는 이유로 코드 재배포가 필요하지는 않습니다.

Meta의 실제 광고 조회 승인이 완료되면 자동 수집 원본과 캡처 확인 자료의 출처를 구분하고 같은 기간을 중복 합산하지 않도록 통합합니다. 지금의 읽기 API가 Meta 광고 조회 승인이나 자동 갱신 성공의 증거는 아닙니다.
